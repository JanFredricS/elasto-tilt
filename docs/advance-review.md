# Advance adversarial review of `PLAN.md`

This is a design review, not evidence that the game or its maps work. The plan has a sensible scope, but the following contracts need to be explicit before the three implementation slices diverge.

## P0 — Define one coordinate and gravity contract

The plan says the map stays fixed while both gravity and the visible world rotate, but does not state their relative signs. With map coordinates `+x` right and `+y` down, let positive `theta` rotate the rendered world clockwise on screen. Screen gravity remains `(0, +g)`, so the physics gravity **in map coordinates** must be `R(-theta) * (0, g) = (g sin theta, g cos theta)`. At `theta = +90°`, map gravity points right; that map-right direction is visually down. The camera/world container rotates around the same chosen screen pivot, while the HUD and input affordances remain unrotated. Angle is continuous internally and wrapped only for display.

Put this convention and a shared `WorldView` snapshot in the API before slices A and B start. Test `0°`, `+90°`, `180°`, and `-90°` against the *rendered* downhill direction, including camera follow. Otherwise both teams can independently implement internally correct but mutually opposite transforms. The input controller should output a signed angular velocity command; calibration, dead zone, smoothing, and the keyboard/touch fallbacks must all feed that same command. Neutral input holds `theta`, rather than easing it toward zero.

The inverted-gravity objects in level 8 add a second gravity rule. Specify whether each body uses ordinary, inverted, or zone gravity at each fixed step. A practical implementation is to keep Rapier's global gravity for ordinary bodies and apply an explicit `-2m*g_map` correction to inverted dynamic bodies, or use zero global gravity and apply `m*g_body` to every dynamic body. Do not silently invert the whole world, since the bicycle, swing weights, and mechanism pieces then become ambiguous.

## P0 — Make bicycle contact mechanics an explicit prototype gate

The bicycle needs one chassis rigid body, two wheel rigid bodies on revolute joints, and a helmet collider or sensor rigidly attached to the chassis. Filter *all* bike internal collider pairs, while allowing wheels and helmet to meet terrain and swings. Collision groups affect contact and events; a broad “bike” exclusion can accidentally suppress helmet deaths or wheel catches. The helmet should trigger a restart on relevant contact with terrain/hazards while apple and exit sensors have their own tags and rules. Use CCD or adequate substeps for small lips and rapid gravity changes; run a stress scenario with repeated full turns and collisions.

Define braking as finite torque or joint motor resistance between each wheel and the chassis, plus tuned wheel/terrain friction. Merely setting wheel angular velocity to zero each frame violates the joint dynamics, and a locked wheel alone does not create a reliable hang. Level geometry must provide visible lips/cradles with dimensions relative to wheel radius and helmet clearance. Prove a wheel catches, the chassis pivots without exploding, and the rider can release and transfer onto a swing *before* authoring several maps around that mechanic. Rapier's [joint guide](https://rapier.rs/docs/user_guides/javascript/joints/) and [collision-group guide](https://rapier.rs/docs/user_guides/javascript/collider_collision_groups/) support the proposed mechanics.

## P0 — Establish a solvable map and time-puzzle contract

Ten named levels are a content list, not ten validated puzzles. Give every level a data entry for spawn pose, bounds, apples, exit, hazards, named mechanic, and one intended route with control actions and expected checkpoints. Validate at least one recorded route through actual physics for each map, with the same collision and camera settings as gameplay. This can be a deterministic input replay plus human visual confirmation; static reachability checks alone cannot prove a wheel transfer or swinging catch. Record failures and retune geometry rather than marking unplayed maps complete. In particular, check the bicycle's *swept wheel, chassis, and helmet clearance* through every corridor and portal-like transition.

For Escher's Orchard, choose one unambiguous rule now: ordinary planar collision geometry under impossible-looking art, or explicit transport portals. The current phrase “rotated room connections” leaves implementers to guess topology. The simpler first version is a fully continuous planar route with visual stair illusions; every visible traversable edge must correspond to a real collider. If portals are intended, their entry/exit transforms must also define bike pose, velocity, gravity angle, camera, and overlap recovery.

For the final puzzle, define a named route coordinate `s` along **static** traversable ground, then advance the selected platform phase by `Δs` and reverse it by `-Δs`. Do not infer direction from screen x, wheel rotation, or a moving platform carrying the bike. Specify path projection at corners, a threshold against jitter, phase limits, and what happens on respawn. Give level 10 a bottleneck whose geometry makes the apple and exit unreachable without moving and then reversing the platform. A recorded successful route should show that temporal reversal is actually necessary. Moving platforms should use Rapier's next kinematic pose before each physics step so contact velocity is computed, with per-step travel bounded to avoid launching or trapping the bike; see [Rapier's rigid-body guide](https://rapier.rs/docs/user_guides/javascript/rigid_bodies/).

## P1 — Freeze slice boundaries and sequence the work

Before parallel implementation, root should freeze a small shared contract: coordinate units and signs; fixed `dt`; `LevelDefinition` collider/object tags and mechanism parameters; physics input commands; immutable render snapshots with interpolated poses; typed game events for apple/death/exit; lifecycle (`load`, `reset`, `pause`, `dispose`); and debug metrics. Physics owns authoritative state and simulation stepping. Renderer consumes snapshots and never mutates physics. Maps use only the declared schema. This is the minimum needed to avoid three incompatible assumptions.

Sequence work as: (1) scaffold/API, (2) a playable Orchard vertical slice proving controls, bike, apples, death, exit, camera, and reset, (3) parallel rendering and progressive map authoring while physics adds catches, swings, inversion, and time mechanisms, (4) integrated route replays and visual/device checks, then (5) release evidence. A first playable slice is especially important because map dimensions and swing timing depend on measured bike behavior. Set a per-level validation status (`draft`, `replay-passed`, `visually-checked`, `device-checked`) so map completion is not confused with file completion.

The stated two fix/review cycles per slice are a useful review budget, but they do not waive the acceptance criteria. A severe remaining failure (unfinishable required level, inverted controls, broken brake transfer, or repeated physics instability) should block a “complete” claim even after cycle two; record it precisely in the residual report. Each fresh review should receive the frozen contract, latest files, tests, and a runnable build, then focus on concrete regressions and user-visible behavior.
